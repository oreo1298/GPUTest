# Decisions

One line per non-trivial choice: what and why. Newest at the bottom of each section.

## Project
- **Working name "Kiln"** (`kiln` GUI, `kiln-run` runner, id `io.github.oreo1298.Kiln`): short, evokes heat/stress testing; defined only in `cmake/AppInfo.cmake` and the generated `gt/app_info.h`.
- **Code namespace `gt::` (not the product name)**: renaming the product never touches code.
- **MIT license**; every dependency must be MIT-compatible (permissive or LGPL dynamically linked) — tracked in THIRD_PARTY.md.

## Environment
- **Mesa 25.2.8 from noble-updates** instead of a PPA: Launchpad (kisak/oibaf PPAs) is blocked by this VM's network policy; 25.2.8 already gives lavapipe Vulkan 1.4 with ray tracing, mesh shaders, AMDX work graphs, descriptor buffer.
- **Local Qt = Ubuntu 6.4 (compile/screenshot fallback); CI/release Qt = aqt 6.8 LTS**: download.qt.io and all Qt mirrors are blocked here; the code guards ≥6.5/6.6/6.8 APIs with `QT_VERSION_CHECK` and implements its own portal/KDE theme reading so behaviour is the same where it matters.
- **Validation layers locally = Ubuntu 1.3.275; CI = LunarG SDK**: sdk.lunarg.com is blocked here; building VVL from source is too heavy for this VM.
- **Dependencies via FetchContent shallow git clones of pinned tags** (codeload tarballs are blocked here; git works everywhere); optional shared clone cache `GT_DEPS_CACHE`.
- **SDL3 built from source (static, video subsystem only)**: no SDL3 package in Ubuntu 24.04; static avoids shipping a DLL; zlib license.

- **Arch package from the checkout (`packaging/arch/PKGBUILD`, `makepkg -si`)**, the same install flow as the
  owner's other projects; it sits in `packaging/arch` instead of the root because makepkg's work folder is `src/`
  next to the PKGBUILD, which at the root is the project's source tree (`makepkg -c`/`-C` would delete it).
  Static `pkgver` (a `pkgver()` function makes makepkg rewrite the tracked PKGBUILD, which blocks `git pull`); CI
  checks it equals `APP_VERSION`, and the README's update command uses `makepkg -sif`. Slang comes from its pinned
  release tarball in `source=()` (no Arch repo package); the other libraries keep coming from FetchContent so the
  pins stay in one place.

## Architecture
- **Two processes (runner + GUI) talking JSON lines over stdout**: a driver crash/TDR kills only the runner; the GUI keeps every event already received.
- **Qt Widgets (not QML) for the GUI**: mature keyboard navigation and screen-reader support, native `windows11` style, cheap custom QPainter graphs, and works with the offscreen platform for screenshots.
- **Custom QPainter charts**: Qt Charts / Qt Graphs are GPL-only in the open-source edition (see RESEARCH.md); custom drawing keeps the app MIT-distributable.
- **SQLite via QtSql (QSQLITE)** for history: ships with qtbase, no extra dependency; the runner itself only writes JSON.
- **CLI11** for runner argument parsing (BSD-3, header-only); **nlohmann/json** for JSON (MIT).
- **volk + VMA** for Vulkan loading/allocation: no link-time dependency on the loader, battle-tested allocator.
- **Thin RHI with D3D11-style slot binding** (b/t/u/s registers per pipeline layout, transient upload ring): trivially maps to Vulkan (push descriptors or per-draw sets), D3D12 (root tables), D3D11 and GL; feature tests use native handles instead.
- **Vulkan bindings derived from HLSL registers** via Slang `-fvk-{b,t,u,s}-shift` (b→0, t→16, u→32, s→48, set 0); push constants at `b13` map to Vulkan push constants / D3D12 root constants / a normal UBO elsewhere.
- **Classic VkRenderPass/VkFramebuffer path with caches** (dynamic rendering optional): works on Vulkan 1.1 drivers for old GPUs.
- **Shaders embedded in the runner binary** (generated C++ arrays via `gt_embed`): no runtime file lookup, single-binary runner.
- **GLSL for OpenGL generated by SPIRV-Cross from Slang's SPIR-V** (Slang's own GLSL output targets Vulkan-flavoured GLSL 450, not GL 3.3).
- **Scenes play a fixed timeline in real time; everything else is deterministic.** A scene pass covers a fixed
  simulated timeline (its camera path) played at wall-clock speed (twice as fast for the quick preset): the camera
  moves at the same speed on every GPU, and a faster GPU renders more frames of the same timeline (as 3DMark and
  Unigine do). This replaced a fixed frame count per pass (frame i at sim-time i·T/N), which an RTX 4090 ran at
  over 3000 fps, so the camera raced through the path and a pass lasted a fraction of a second, while a slow GPU
  needed minutes for the same frames. The timeline, seeds and content stay fixed, so scores remain repeatable (the
  sampled frames differ, the average over the timeline does not). Smoke runs (CI) keep the deterministic frame
  sequence, and golden frames are always rendered at fixed times. Diagnostics and other frame loops stay
  deterministic. A per-test wall-clock cap still flags (not hides) very slow devices.

- **Per-API capability listings generated from vk.xml** (`scripts/gen_vk_caps.py` → `vk_caps_gen.inc`, committed): a complete, version-matched feature/property explorer without hand-maintained tables or a Python build dependency.
- **Every supported "interesting" Vulkan feature is enabled at device creation**, except features that change workload behaviour (robustBufferAccess, robustImageAccess, capture-replay, protected memory).
- **When the installed validation layer is older than our headers, the device is limited to what the layer knows** (API 1.3, newer extensions off) and capability queries are muted: otherwise the layer reports false errors. CI uses the current LunarG layer, so real errors are still caught.
- **Swapchain present mode: IMMEDIATE, then MAILBOX, then FIFO** when vsync is off.
- **Frames in flight = 2; frame time = interval between successive submissions** (the CPU blocks on the frame two back), GPU time from timestamps around the test's own work (excludes blit/HUD).
  Golden frames are rendered and dumped before the warm-up (dumping drains the GPU, which must not happen between
  timed frames); the warm-up is 30 frames or 2 s, whichever comes first.
- **Run length per duration preset.** Scenes: quick plays the timeline once at double speed, standard once, extreme
  three times (a 30 s timeline: 15 s, 30 s, 90 s). Deterministic loops repeat whole passes until the preset's minimum
  time (quick 8 s, standard 25 s, extreme 90 s). A hard time limit (90/240/900 s) marks results `time_limited`.
- **Scene weight targets a high-end GPU at the default 1080p / high.** The owner's RTX 4090 ran the first scenes
  in 0.2-2.3 ms of GPU time (Glasshouse 0.22 ms, Gallery 2.2 ms, Atrium 0.23 ms, Lattice 0.20 ms): far too light to
  tell fast GPUs apart. Content and ray budgets were raised so that a 4090 needs roughly 2-6 ms at high, more at
  ultra, while low stays usable on integrated GPUs; the quality preset is the knob between them. Calibration
  follows from real results (the VM's software renderers only give rough ratios, see Environment).
  - Glasshouse: twelve trees and 24 shrubs of alpha-tested leaf cards (up to 9000 per tree) in the BVH, so every
    ray tests leaf shapes as real foliage does; glass panes (analytic planes with a reflection ray each); eight
    grass beds (up to 400k mesh-shader blades); per pixel 1/2/4 soft-shadow rays, 1/2/4/8 AO rays, 0/1/2/4 GI
    rays with a shadow ray at each hit and an a-trous filter (low/medium/high/ultra), plus reflection rays with
    hit shadows. Rough reflection and GI rays see the sky without the sun's disc (the direct term has the sun).
- **Generated content uses a portable random generator** (`scene::Random`, SplitMix64): the std:: distributions
  differ between libstdc++ and MSVC, which would make the same scene differ between Linux and Windows builds.
- **Golden-image checks use a 16×9 mean-colour signature with a tolerance (default 8/255) plus an exact hash**: exact hashes break across drivers/LLVM versions, signatures still catch broken rendering.
- **Tests are linked as an OBJECT library with static self-registration** (`GT_REGISTER_TEST`): adding a test is one file, and the linker cannot drop it.
- **HUD font: public-domain 8×8 VGA font** taken from SDL3's debug-text font (no font dependency).
- **Telemetry: provider chain per GPU, earlier providers win per channel**; VRAM falls back to VK_EXT_memory_budget. Samples at 10 Hz on a background thread.
- **NVML via our own prototypes** (nvml.h may not be redistributed).
- **AMD on Windows: ADL + D3DKMT instead of ADLX** — the ADLX SDK license is proprietary and forbids use in free-software projects (see RESEARCH.md); ADL headers carry MIT notices and we declare our own prototypes. (Deviation from SPEC §3.)
- **Intel on Windows: Level Zero Sysman (MIT) + D3DKMT instead of IGCL** — IGCL's license is Intel-specific, not MIT-compatible. (Deviation from SPEC §3.)
- **No DLSS code in the repository**: the DLSS SDK license forbids exposing it under an open-source license. XeSS (MIT headers, redistributable DLLs) can be an optional runtime plugin; FSR 1/2/3.1 (MIT) are built in.
- **Safety defaults: 90 °C GPU, 105 °C hotspot, 100 °C memory, sustained for 2 s**: below every vendor's own shutdown limits, above normal gaming temperatures, so false aborts are rare.
- **Runner control via stdin** (`--control-stdin`, command `stop`; EOF = controller gone): portable, unlike signals to GUI-spawned processes on Windows.

- **GUI: Fusion style + palette built from the system on Linux, native `windows11` style on Windows**; custom widgets (cards, badges, nav, charts) paint with ThemeManager colours instead of a global style sheet, so native widgets stay native.
- **KDE: read the Plasma colour scheme from kdeglobals (watched + KGlobalSettings D-Bus signal)**, because the AppImage's Qt cannot load Plasma's platform-theme plugin (built against the distro Qt). **Others: xdg-desktop-portal color-scheme and accent-color** (Qt does not read the portal accent colour itself).
- **Chart colours: the validated reference categorical palette (light/dark steps) and fixed status colours**; series keep their colour slot when toggled; text never uses series colours.
- **Icons: Lucide (ISC), tinted at runtime from the palette** so they follow light/dark/accent.
- **The GUI learns everything from the runner** (`--list-devices/--list-tests/--list-suites/--sysinfo/--caps/--check-support --json`) and runs benchmarks as a child process with `--progress jsonl --control-stdin`; no GPU code in the GUI process.
- **`--screenshots DIR` debug mode** renders every page in light and dark (with `--results`/`--replay` for data) — used for UI review and docs.
- **CI failure triage via annotations**: logs live on blob storage this VM cannot reach, so CI turns error lines into `::error` annotations readable through the REST API (the GitHub MCP `get_job_logs` tool also works).

- **Run history = SQLite index over the results folder; the JSON files stay the source of truth.** The database
  (`<data dir>/history.sqlite`, QtSql/QSQLITE) can be deleted at any time and is rebuilt by rescanning; "Forget"
  records the path in a `forgotten` table so rescans do not re-add it, an explicit import clears that.
- **Compare matches tests by id; scores are averaged over loops, frame data comes from the first loop.** Differences
  under ±2 % are shown as "about the same" (no arrow), larger ones with ▲/▼ coloured by better/worse; the sign in
  the text carries the same information, so colour is never the only cue. Runs with different comparable keys can
  still be compared, with a warning naming the settings that differ.
- **Frame-time histogram: y = share of frames (%), "nice" bin width over the 0.5–99.9th percentile range**, slower
  frames counted and reported as "beyond axis" rather than dropped; two runs share one bin layout.
- **Telemetry charts are small multiples, one per unit** (°C, W, MHz, %, rpm, GiB) — never two y axes; throttle
  periods are shaded on every chart (warning = power/driver limits, serious = thermal/current/voltage, critical =
  hardware slowdown) and listed in the hover tooltip.
- **Icons are tinted when painted** (a QIconEngine reading the current palette), so every icon follows live theme
  changes without its owner re-creating it.
- **TabView instead of QTabWidget for content tabs**: QTabWidget/QStackedLayout size to the tallest page (QStackedLayout's
  height-for-width is the maximum over all pages), which left large empty areas under short tabs.
- **Windows CI installs the newest Qt that aqt can fetch** (configured 6.12.0, falling back through older minor
  releases) instead of pinning: aqt currently cannot read 6.12.0's Windows repository metadata.

- **Device losses are recorded, not just reported**: `device_losses` holds the test, time, the driver's fault
  report (`VK_EXT_device_fault`, enabled whenever supported; vendor binary dumps stay off) and the last sensor
  sample. With `--on-device-lost recover` the runner recreates device and window, keeps the telemetry gathered so
  far and continues with the next test; the exit code stays 5 so scripts notice, and the loss is the headline of
  the results page.
- **Testing hooks instead of untested error paths**: `GT_FAKE_TELEMETRY` (synthetic sensors) and the `debug`-tagged
  `debug.device_lost` test let CI (including the ASan job) drive the safety cutoff, device-loss abort and recovery,
  stdin stop and timed loops on lavapipe. Neither is reachable without explicitly asking for it.
- **Safety cutoff messages state the rule**: "stayed above the 90 °C limit for 2 s (reached 93 °C)", so a user can
  tell a cutoff from a crash and knows which limit to look at.

- **Diagnostics are judged by the GPU against itself**: artifact detection compares re-rendered reference frames
  bit for bit with the first rendering, the float compute chain with the first GPU round, and only exact integer
  results with the CPU. Cross-vendor or CPU float comparisons would flag harmless rounding differences.
- **VRAM test coverage scales with the preset** (smoke 64 MiB, quick 50 % of free up to 4 GiB, standard 90 %,
  extreme 92 % of free VRAM; integrated GPUs at most a quarter of free memory and 2 GiB, because that is system
  RAM). Chunks are 256 MiB so every dispatch stays far below OS GPU watchdogs; all chunks are written before any is
  verified so data has to be retained. Addresses are reported as chunk + offset (physical addresses are not exposed).
- **Thermal-soak verdicts**: FAIL on wrong reference frames or hardware slowdown; WARN on > 10 % performance drop,
  > 5 % of the time thermal-throttled, or ≥ 87 °C GPU / ≥ 100 °C hotspot; power-limit throttling alone is normal.
- **PCIe verdicts are WARN at worst** (lower gen/width than the card supports, < 50 % of the link's bandwidth):
  boards and CPUs legitimately limit links, so the message names the likely causes instead of failing the card.
- **Every detector is proven in CI by fault injection** (`diag.*.inject`), since a detector that never fires is
  indistinguishable from a broken one.

- **Micro-benchmark timing**: GPU timestamps around a submission of R repetitions, R calibrated so a submission
  lasts ~10 ms (2 ms at smoke size, 20 ms for transfers) — far above timer resolution and launch overhead, far
  below OS GPU watchdogs; the result is the median per-repetition time of 2/5/9/15 samples (smoke/quick/standard/
  extreme) with the spread recorded. Operation counts: FMA / multiply-add = 2 ops, 4×int8 dot = 8 ops; copy
  bandwidth counts bytes read + written; fill rates count pixels/texels written/read, not bytes.
- **Synthetic workloads are sized for the hardware class**: 1 Mi threads and 512 MiB buffers on real GPUs (beyond
  the largest last-level caches, e.g. 128 MB Infinity Cache), much smaller on software renderers, whose numbers
  only prove the code works.
- **ALU kernels use 8 independent chains with runtime constants** so no compiler can fold or shorten them; the
  int8 kernel feeds each dot product's result back as its packed input for the same reason.

- **Ray tracing in the RHI**: each acceleration structure owns its storage and its build scratch (no shared
  scratch pool to synchronise); TLAS instance records go through per-list upload memory into a device-local
  instance buffer; ray-tracing pipelines own a shader binding table laid out raygen | misses | hit groups. Builds
  mark the list dirty and the next draw/dispatch/trace gets an acceleration-structure barrier automatically
  (`accelBarrier()` exists for build-after-build). Vulkan only until D3D12 (M10) implements the same interface.
- **Feature tests check their own results** — BVH probe rays against a CPU reference (before and after a refit),
  ray queries vs pipeline per ray, mesh vs vertex pipeline images, VRS coarse-shading probe, subgroup ops against a
  CPU model of the reported lane layout, every bindless table entry, SER and opacity micromaps vs their plain
  versions bit for bit, cooperative matrices against exact CPU products. A feature that is fast but wrong FAILs.
  `feature.rt.bvh.inject` proves the probe check in CI.
- **Hardware-only features keep a runnable baseline**: SER and opacity micromaps are not in lavapipe, so their
  tests take `baseline_only=1` in CI to run everything except the feature itself; VRS and cooperative matrices are
  gated and skip with the exact missing extension.
- **SER uses VK_EXT_ray_tracing_invocation_reorder only** (what Slang emits by default); GPUs with only the NV
  extension skip with "update the driver". HLSL SER needs SM 6.9 — added with the D3D12 backend if its DXC has it.
- **Opacity micromaps at subdivision level 0** (one 4-state value per triangle, one byte per micromap triangle):
  avoids the bird-curve micro-triangle ordering, which cannot be verified without hardware, while still moving the
  alpha test of fully inside/outside triangles into traversal. VK_EXT_opacity_micromap now; the new
  VK_KHR_opacity_micromap (micromaps as acceleration structures) when drivers ship it.
- **Texture tables (bindless)** are descriptor set 1 / `space1`: one partially bound, variable-count sampled-image
  array (update-after-bind when supported), capped at 65 536 and below the per-stage limits; ordinary bindings stay
  push descriptors in set 0. Descriptor buffers are reported, not used.
- **Pipeline-compilation test salts SPIR-V**: a 32-bit constant in the fragment shader is patched with a random
  value per pipeline and per run, so neither the driver's memory cache nor its disk cache has seen the pipeline
  (cold), then the same pipelines are created again (warm). Parallel compilation uses up to 8 threads; the render-
  pass cache is mutex-protected for it.
- **Ratios are shown, not scored** (VRS speed-up, async/copy overlap gain, SER/OMM speed-up, draw-call and
  pipeline-compile costs, which mostly measure the CPU and driver); absolute rates with a clear hardware meaning
  (BVH Mtri/s, Grays/s, mesh Gtri/s, subgroup and bindless rates, matrix TFLOPS) get provisional references.
- **Not in M8, recorded**: Vulkan work graphs (only the provisional VK_AMDX_shader_enqueue exists and Slang has no
  SPIR-V node shaders) — D3D12 work graphs come with M10; cooperative vectors (NVIDIA-only on Vulkan) move to M10
  with Shader Model 6.9's cross-vendor version; image-based VRS (Vulkan attachment rate / D3D12 tier 2) moves to M10.
- **Shader manifest defines are comma-separated** (`defines=A=1,B=2`): CMake turned `;` into list separators.
- **No local DXC/fxc**: Windows compiler binaries can be downloaded but this environment does not allow running
  them, so D3D shader compilation is verified only by Windows CI (which builds with `-k 0` to report every error).

- **D3D12 backend binding model**: one root signature per pipeline layout (cached): push constants as root
  constants at b13, buffers and acceleration structures as root descriptors (moved into the table only when a
  layout would exceed the 64-DWORD limit), one descriptor table for texture views and one for samplers, filled by
  copying CPU-heap descriptors into per-command-list blocks of the shader-visible heaps at draw time.
- **D3D12 resource states**: buffers and simultaneous-access textures (`concurrentQueues`) decay to COMMON after
  every ExecuteCommandLists, so they are tracked per command list from COMMON, and submit() executes one list per
  call; other textures are tracked globally (record order = submit order, as with Vulkan layouts). Every binding
  transitions its resource to a usable state, so tests written against Vulkan's laxer rules still work.
- **D3D12 runtime selection at run time**: d3d12.dll/dxgi.dll are loaded dynamically; when "D3D12\D3D12Core.dll"
  sits next to the runner, devices come from that Agility SDK through ID3D12SDKConfiguration1::CreateDeviceFactory,
  otherwise from Windows' built-in runtime. No D3D12SDKVersion export, so a missing folder can never break startup.
- **Agility SDK and WARP are not shipped**: WARP's NuGet license is test-only; the Agility SDK's redistribution
  terms require end-user terms that protect Microsoft and an indemnity from the distributor, which is the owner's
  call (asked). CI stages both next to the test build only; the portable zip uses Windows' runtime.
- **DirectX-Headers v1.619.5** (MIT) for the API (no Windows SDK d3d12.h); the backend is compile-checked on
  Linux with mingw-w64 (`scripts/check-d3d12.sh`) because nothing can run Windows binaries here.
- **Cross-queue hand-over on D3D12**: depth and MSAA textures cannot use simultaneous access, so a graphics-list
  `transition(ShaderRead)` of a `concurrentQueues` texture uses NON_PIXEL_SHADER_RESOURCE (valid on the compute
  queue) and compute dispatches only require that state; pixel-shader binds add PIXEL_SHADER_RESOURCE.
- **Shading-rate images (VRS tier 2) on D3D12 only for now**: `RenderPassDesc::shadingRateImage` (R8_UINT, codes from
  `rhi::shadingRateCode`, shared by D3D12 and Vulkan) overrides the per-draw rate. The Vulkan attachment rate needs
  a render pass with a fragment-shading-rate attachment, which changes render-pass compatibility for every
  pipeline used with it; with no Vulkan driver here or in CI that supports it (lavapipe has no
  VK_KHR_fragment_shading_rate), that path would be written blind, so it waits for hardware testing (M14).
- **Native D3D12 feature tests**: features with no Vulkan counterpart (sampler feedback, work graphs) record D3D12
  commands directly between `D3D12CommandList::beginNative()` / `endNative()` (barriers flushed first, root state
  re-bound after), with their own root signatures and descriptors borrowed from the device heaps, so they still use
  the harness's timing (`measureMicro`) and state tracking for RHI resources.
- **Work-graph shaders are HLSL compiled by DXC**: Slang has no node shaders, so `shaders/manifest.txt` accepts
  `.hlsl` entries (D3D12 only) compiled with DXC ≥ 1.8 on Windows (`DXC_DIR`, CI uses the NuGet DXC that also
  backs slangc). Without a suitable DXC the build still succeeds and the test reports the shaders as missing. The
  test graph is deliberately simple (broadcasting entry → thread-launch leaf) so every record can be checked;
  its throughput is shown next to the same work as one dispatch (ratio, not scored).
- **Pipeline-compilation test stays SPIR-V only**: DXIL keeps constants in LLVM bitcode (variable-width fields)
  and containers carry a hash, so per-run salting would need a bitcode rewriter and re-hashing; build-time
  variants would be cached by the driver's disk cache after the first run, which defeats a cold measurement.
- **D3D12 SER = raytracing tier 1.2 + shader model 6.9** (DXR 1.2); Slang emits native `dx::HitObject` /
  `dx::MaybeReorderThread` for lib_6_9, so the SER test shares its shader with Vulkan.
- **D3D12 opacity micromaps mirror the Vulkan ones**: one OMM array per geometry with a 4-state, subdivision-0
  micromap per triangle, linked through a 32-bit index buffer, built in the first `buildBlas`. D3D12 honours OMMs
  in ray queries only with `RAYQUERY_FLAG_ALLOW_OPACITY_MICROMAPS`, which Slang's `RayQuery` cannot express yet,
  so the OMM test uses an HLSL copy of its shader on D3D12 (`omm_dxr.hlsl`, DXC, cs_6_9) for both passes.
- **Cooperative vectors**: D3D12's are preview-only (absent from the retail Agility SDK and DirectX-Headers) and
  Slang has no HLSL path for them; on Vulkan only VK_NV_cooperative_vector exists (reported in caps).
- **Sampler feedback is verified exactly**: one point sample per mip region at a chosen mip, with mips no larger
  than a region and sample positions off every texel edge, so the decoded MinMip map is fully predictable; finer
  than expected counts as conservative (warn), coarser as wrong (fail).

- **OpenGL shaders: SPIR-V -> GLSL with SPIRV-Cross at build time** (`gt_glslgen`, Apache-2.0, not shipped).
  GL has no descriptor sets, so resources get names derived from their RHI slot and a binding table in comment
  lines; the backend assigns binding points per program at link time (works on GLSL 330 and 4xx alike).
  Varyings are named by location so separately compiled stages link on GLSL 330. Clip space is D3D's: the
  generator flips y and rewrites depth to [-w, w], so memory row 0 is the image top as on D3D/Vulkan — GL frames
  match the Vulkan golden frames (max channel difference 1 on llvmpipe) and front faces map to the mirrored GL
  winding. Ray tracing, mesh shaders and VRS have no GL path.
- **OpenGL backend model**: command lists record closures into an arena and the device replays them at submit
  on the context thread; one ordered stream for every queue type (no async compute/copy), fences via
  glFenceSync; an executor holds the RHI's b/t/u/s slot tables and binds what the current program uses. GL 3.3
  core is the floor, plus ARB_buffer_storage (persistently mapped upload/readback memory) — every GL 3.3-class
  driver still in use has it. Compute, storage buffers/images, texture views, multi-draw indirect are used from
  4.2/4.3 when present. The context lives on a hidden window of its own and is made current on a swapchain's
  window only to present (blit + swap); headless Linux uses SDL's offscreen (EGL) driver. Entry points load
  through SDL_GL_GetProcAddress — nothing links against libGL/opengl32. Software GL (llvmpipe) reports no GPU
  timestamps: it runs compute and copies in the API thread but captures timestamps later in its rasterizer
  threads, so the harness times with the CPU clock there.
- **Direct3D 11 backend model**: the OpenGL model again — closures recorded into a shared `CommandArena` and
  replayed on the immediate context at submit (deferred contexts would serialise on most drivers anyway), one
  ordered stream for every queue type, completion through event queries, every submission inside a
  timestamp-disjoint query. Feature level 11_0 is the floor: every embedded D3D11 shader is shader model 5, and
  FL10 hardware (2006–2009) is out of scope. d3d11.dll/dxgi.dll are loaded at run time like D3D12's.
- **D3D11 memory**: Upload and Readback buffers are CPU copies (D3D11 cannot map GPU memory persistently).
  Upload data reaches its GPU buffer once per submission, when a command first reads it (transient chunks copy
  only their used bytes); readback copies go through staging resources and land in the CPU copy when the
  submission retires. Uniform data and push constants (b13) use per-slot dynamic constant buffers in five size
  classes, written with Map(WRITE_DISCARD) at replay, so a rename keeps the binding valid.
- **D3D11 views follow the shader's reflection**: D3D11 views must match the declaration (structured buffer of a
  given stride, raw buffer or texture), and the RHI's buffers do not say which they are. Pipelines parse their
  DXBC's RDEF chunk (`src/rhi/dxbc_reflect.cpp`, unit-tested on Linux); storage buffers without vertex, index or
  indirect use are created when first used, structured with the stride the first shader declares (or raw), and
  are re-created with their contents if a later shader wants another layout. CPU-side data read as a structured
  buffer by a shader when its buffer cannot take that layout (transient memory) is copied to a dynamic
  structured buffer. Resources a draw or dispatch writes are unbound from inputs first, so the runtime never
  silently nulls a binding.

- **FSR 1 is ported, not linked**: the 32-bit EASU and RCAS paths of AMD's MIT `ffx_fsr1.h` live in Slang
  (`shaders/src/upscale/fsr1.slang`), one thread per output pixel, so they build for every API from the same source
  (GLSL needs 4.30 for gathers and images). The packed FP16 paths are left out: they need FP16 support everywhere.
  RCAS's divisions are guarded for black and white neighbourhoods (GLSL min/max do not promise to drop NaNs).
- **Upscaling is a run setting for scenes**: with `--upscale fsr1|bilinear`, scene tests see a `RunSettings` whose
  width/height are the render size (output / 1.3, 1.5, 1.7 or 2.0) and the frame loop upscales their output before
  presenting, hashing or dumping it; the upscale pass is inside the frame's GPU time. No scene code changes. The
  upscaler and mode join the comparable key (only when not off, so native keys are unchanged).
- **feature.upscale judges FSR against bilinear on supersampled content**: comparing with a native render that is
  itself aliased rewards blur (FSR's sharpening loses PSNR there), so the test renders an analytic image with 4x4
  supersampling at every size and requires EASU's PSNR to be at least bilinear's minus 0.5 dB.

- **DLSS and XeSS: licenses checked (2026-10-27), plugins only.** XeSS SDK (github.com/intel/xess): the public
  headers became MIT on 2026-09-09 (commit de0fb9c; tagged releases up to v3.0.2 still carry Intel's proprietary
  notice, so the headers are vendored from that commit); the runtime (`libxess.dll`) is under the Intel
  Simplified Software License — redistributable unmodified with its notice, no reverse engineering. NVIDIA DLSS SDK (github.com/NVIDIA/DLSS):
  NVIDIA RTX SDKs license — distribution only in object form inside an application whose terms are "at least as
  protective" as NVIDIA's, and the SDK must not become subject to an open-source license (section 3e); its headers
  and libraries are not MIT. NVIDIA Streamline (github.com/NVIDIA-RTX/Streamline) is MIT, but the DLSS binaries it
  loads are not. Consequences: Kiln ships neither vendor's binaries. Third-party upscalers load at run time
  through a small MIT C interface (`src/bench/gt/bench/upscaler_plugin.h`, docs/PLUGINS.md), off by default
  (`--upscaler-plugins`). The XeSS plugin (our code, from the MIT headers) ships in the Windows zip and needs the
  user's `libxess.dll`; CI downloads that DLL only to test the plugin. A DLSS plugin can only be built by a user
  from NVIDIA's SDK under NVIDIA's terms, so none is in this repository.

- **HDR check without colour-managed rendering**: `feature.hdr` writes PQ-encoded BT.2020 values directly into an
  RGB10A2 image and the presenter, switched to an HDR10 swapchain (`Presenter::setHdr`), shows them as they are.
  The encoding is verified against a CPU encoder on every run (offscreen too); the display part needs a person to
  look, plus what DXGI reports (colour space, luminance range). Vulkan HDR10 uses A2B10G10R10 only (the RHI's
  RGB10A2); the HUD is off on HDR swapchains (its white would be 10000 nits).

- **Video engines through native Vulkan Video** (`feature.video`). The RHI gets no video abstraction: video
  sessions, DPB slots and bitstream buffers do not fit its resource model and only one test uses them, so the
  RHI only creates the video decode/encode queues and exposes them, with the enabled extensions, through
  `NativeDevice`; the test drives volk directly (`video_vk.h`: a codec-independent decoder and encoder,
  codecs plug in as `DecodeCodec` / `EncodeCodec`).
- **Decode throughput on fixed reference streams, checked bit for bit.** `data/video` holds one 1080p stream per
  codec (8 frames, IDR/key frame + inter frames referencing the previous frame, ~25 Mbit/s at 60 fps), made by
  `scripts/make-video-streams.py` with FFmpeg's libx264/libx265/libaom from Kiln's own synthetic pattern, plus
  the CRC-32 of each frame FFmpeg decodes. Every GPU decodes the same bits (comparable frame rates), and as the
  codecs define decoding exactly, a GPU frame that differs from FFmpeg's is a decoder fault. The streams are
  embedded with `gt_embed` (~1.3 MB). Encoder output is not covered by the encoders' licenses and the content
  is ours, so the streams are MIT like the rest (`data/video/README.md`). The same streams validate the
  bitstream parsers in unit tests against values from FFmpeg's `trace_headers` filter.
- **Encode throughput on the GPU's encoder, checked by a round trip.** The same pattern (identical bytes from
  the C++ and Python generators) is encoded as IDR + P-frames, constant quantizer where the encoder offers rate
  control "disabled", else the driver's default; the stream is decoded on the GPU with the parameter sets the
  encoder actually wrote (`vkGetEncodedVideoSessionParametersKHR`, parsed: encoders may override) and the
  slice headers it produced; luma PSNR against the source warns below 30 dB and fails below 25 dB. A GPU with
  an encoder but no decoder reports encode fps unchecked.
- **Video details:** throughput = wall time of submissions of 8 back-to-back GOPs after one warm-up. Decoding
  puts frame f in DPB slot f and image layer f (any frame may reference any earlier one, as AV1 needs);
  H.264 references follow the sliding window. Slice offsets point at start codes, as FFmpeg's Vulkan decoder
  does (the spec text says "slice headers"). All native submissions are ordered by one timeline semaphore;
  images that cross queues use concurrent sharing. No driver here or in CI has video queues (lavapipe, WARP),
  and building the Khronos mock ICD to run the validation layers over this code was not allowed in this
  environment, so the Vulkan calls were checked against the spec text and are verified on hardware
  (docs/HARDWARE_TESTING.md).
- **AV1 in `feature.video`.** The reader (`av1_params.h`) parses OBUs, the sequence header and the full
  uncompressed frame header, carrying the reference state between frames (order hints, loop filter deltas,
  segmentation, global motion, as in AV1 section 7.20) because Vulkan wants the resolved values; CDEF secondary
  strengths stay as coded and loop restoration sizes are passed as log2 - 5, as Vulkan's `StdVideoAV1*` structs
  define them. It is checked against FFmpeg's `trace_headers` on the reference stream and on two small libaom
  streams with 2x2 tiles + segmentation and with global motion (`tests/data/video`, made by the same script).
  Hidden frames, `show_existing_frame`, short reference signalling, film grain and large-scale tiles are refused
  with a reason (no reference or GPU-encoded stream uses them). The encoder writes a key frame and 7 inter frames
  that predict from LAST_FRAME only, with `primary_ref_frame` = none (each frame starts from default CDFs), at a
  constant `base_q_idx` 110 where rate control can be disabled; it needs the `videoEncodeAV1` feature, which the
  device now enables when offered. The spec does not say whether encoders write OBU size fields, so the output
  of each encode is normalised (`av1::withSizeFields`) before the frames are joined and read back.
- **Direct3D 12 Video in `feature.video`: decode through DXVA buffers.** `video_dxva.cpp` turns the same parsed
  streams into DXVA picture parameters, inverse quantization matrices and short-format slice / AV1 tile entries
  (Microsoft's DXVA H.264, HEVC and AV1 specifications; Mesa's MIT-licensed d3d12 video driver was read as a
  reference for the field semantics, no code taken). The decoder (`video_d3d12.cpp`) gives each GOP frame its
  own NV12 picture, so the DXVA picture index of frame f is f: separate textures on decode tier 2 and up (how
  such decoders are usually driven, and what Mesa does), the slices of one texture array on tier 1 (which only
  takes that). Decoders that require reference-only allocations get a second set written through the output
  conversion. Each frame's picture is in VIDEO_DECODE_WRITE and every other in VIDEO_DECODE_READ while it
  decodes, everything else in COMMON; the bitstream is copied once into a default-heap buffer (frames at
  256-byte offsets, zero-padded to 128 bytes), so throughput does not include uploads. The pictures that are
  read back are filled with 0xA5 before decoding, so a frame the decoder never writes is reported as such
  (`decode_unwritten`) instead of as a wrong checksum: WARP returned all-zero frames with a status of "ok", and
  the fill showed that it writes nothing (and that the read-back works). A trial that also put the stream's
  SPS / PPS into the bitstream (ahead of or inside the first slice entry) changed nothing on WARP and was
  removed again: DXVA decoders take those values from the picture parameters. Reference resolution
  (H.264 sliding window, H.265 RPS, AV1 slot map) moved into the parsers so both APIs use the same code.
  AV1 streams with rotation / affine global motion are refused on D3D12 (DXVA wants each model's validity,
  AV1 7.11.3.6, which is not derived); the reference stream has none.
- **Direct3D 12 Video encode: H.264 and H.265, parameter sets written by the test.** D3D12 encoders write slice
  data only, so `video_d3d12_encode.cpp` settles a configuration with the support queries (profile High then
  Main for H.264, Main for H.265; CABAC / 8x8 transform / SAO where offered; the largest CTU and transform sizes
  the encoder takes; constant QP 26 / 28; one slice; GOP of 8 with POC type 2, else 0) and writes the SPS / PPS
  (and VPS) the D3D12 encoding specification gives for it, with `h264::write` / `h265::write`. The
  specification's tables were checked against the header (its enum values and some names are out of date) and
  read by a subagent; where it is ambiguous the choices are: H.264 cropping at the bottom (the table says top,
  which no decoder expects), H.265 picture size aligned to the encoder's block size with a conformance window.
  H.264 asks for an 8-bit frame_num (`log2_max_frame_num_minus4` 4): WARP's encoder writes 8 bits whatever the
  GOP structure says (its first P slice parses to frame_num 1 only that way), and the SPS must match the slices.
  Slices without an Annex B start code get one. The joined stream is decoded on the D3D12 decoder for the
  round-trip PSNR. Reconstructed pictures are a two-slice reference-only array used in turn; recon in
  VIDEO_ENCODE_WRITE and the reference in VIDEO_ENCODE_READ around each EncodeFrame (states the specification
  leaves unstated, taken from the resource-state names).
- **AV1 encode on Direct3D 12: headers written from the post-encode values.** The D3D12 AV1 encoder writes tile
  data only; the application writes the sequence header, frame header and tile group (Microsoft's D3D12 AV1
  encoding specification; Mesa's MIT-licensed d3d12 encoder, itself a client of this API, was read to confirm
  how the values map onto syntax). `av1::writeSequenceHeader` / `writeFrame` are the parser's mirror image and
  are tested by rewriting every header of the three AV1 test streams bit for bit (tiles, segmentation, global
  motion, loop restoration). Configuration: AV1 Main, level 4.1 or the suggestion, only the coding tools the
  encoder requires (plus order hints when a required tool needs them), a fixed 8-tap filter and transform
  selection where offered, one tile (else the smallest uniform grid the encoder takes), constant base_q_idx
  110 as on Vulkan, fixed deblocking levels and no CDEF strengths of our own; SUPPORT1 checks the whole set (the
  older query refuses AV1). Each frame takes the quantizer, loop filter, CDEF, compound mode, primary
  reference and reference indices from the resolved post-encode values where the encoder reports that it
  chooses them. Every frame refreshes all eight reference slots, so the DPB only ever holds the previous
  frame (the one reconstructed texture the GOP keeps). Each frame is a temporal unit (temporal delimiter,
  the sequence header on the key frame, one frame OBU), checked by decoding it again on the D3D12 decoder.
- **WARP's video engines are opt-in.** WARP (1.0.13 and later) decodes and encodes H.264 / H.265 through Media
  Foundation on the CPU, so `feature.video` skips software adapters unless `--param feature.video.software=1`
  is given: it is not a GPU measurement and it hung the first CI run. CI runs it in a separate, bounded,
  report-only step, which exercises the DXVA and encoder paths that no GPU runs there.
- **A stuck video engine fails its codec instead of hanging the run.** Every Direct3D 12 video wait gives up
  after 20 s; the codec then reports the failure and the next codec runs. The decoder or encoder whose work
  never finished is deliberately not released (nor the encode configuration its commands came from): releasing
  objects the GPU still uses hung WARP, so they stay allocated until the runner exits.

## Packaging and releases
- **Flatpak on the KDE runtime, built offline.** `packaging/flatpak/<APP_RDNN>.yml` uses org.kde.Platform 6.11
  (Qt 6 with Wayland, SQLite and Vulkan loader included); the libraries CMake normally fetches are pinned git
  sources fed through `GT_DEPS_CACHE` (each with its `.gt-tag`), and Slang is a build-time archive that is not
  installed. Permissions: Wayland / X11, IPC and `--device=dri` (which includes NVIDIA's nodes); no host files
  (the file dialogs use the portal). CI builds it in the Flathub-infra container and checks the pins against
  `cmake/Dependencies.cmake`. The local `dir` source builds the checkout; a Flathub submission would swap it for
  a tagged git source.
- **Windows installer with Inno Setup.** Built from the same staged folder as the portable zip (minus its
  `portable.txt` marker), per-user by default with an all-users option, Start menu entry, optional desktop icon
  and uninstaller. The AppId GUID in `packaging/windows/installer.iss` must never change. Packaging found that
  `windeployqt` had never run (the script read `APP_GUI_NAME` as the literal `${APP_ID}`), so earlier portable
  zips lacked the Qt DLLs; fixed.
- **Releases from tags.** Pushing `v<APP_VERSION>` runs the normal CI jobs and then `release`, which refuses a tag
  that does not match `APP_VERSION`, collects the AppImage, Flatpak bundle, Arch package, portable zip and
  installer, writes `SHA256SUMS` and creates the GitHub release with that version's CHANGELOG.md section as notes.

## Stats & scoring
- **1%/0.1% lows = 1000 / mean of the slowest 1%/0.1% of frame times** (at least one frame); percentiles use linear interpolation (R-7).
- **Scores: 1000 × value / reference per test, geometric means for subscores and overall** (not a harmonic mean); comparable only with identical `suite|api|resolution|quality|duration`.
- **Stutter = frame slower than 2× the median of the previous 32 frames and +4 ms over it**: ratio alone flags imperceptible spikes at very high FPS.
